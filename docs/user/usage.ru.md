Все параметры, значения по умолчанию и области действия лимитов перечислены
в [полном справочнике команд и флагов](../reference/cli.ru.md). `scout -h` печатает
полный список в терминале; `scout scan -h` показывает флаги сканирования.

## Первая проверка

Используйте `scout` из `PATH` или замените его путём к вашему бинарнику. Примеры
работают из любого каталога; пути проверяемых папок считаются от текущего каталога.
Установка описана в [руководстве сборки](../development/native-build.ru.md#установка-и-пути-сборки).

```sh
scout doctor
scout scan ./my-skill
scout scan --format markdown --output /tmp/scout-report.md ./my-skill
scout compare ./previous ./candidate
```

Замените пути в примерах своими локальными папками навыков или плагинов. Проверка
по умолчанию не требует конфигурации и API-ключей и не делает сетевых запросов.
Scout анализирует пакет без выполнения его кода. Сохраняйте отчёты вне проверяемых
каталогов.

Смотрите `Findings` — обнаруженные проблемы, `Completeness` — завершённость
проверки и `Decision` — решение политики: `allow`, `review` или `block`.
`review` возможен и без находок, если ограничения анализа требуют ручной проверки.

Указывайте параметры перед позиционными входами. `--` завершает разбор параметров;
для обычных путей он необязателен. Сохраняйте его перед путём из переменной
или именем, начинающимся с `-`:

```sh
scout scan --format json -- "$target"
```

`scan` принимает до 32 входов; `batch` — другое имя той же команды. `--target-workers` задаёт параллелизм
входов, `--workers` — анализаторов, `--timeout` ограничивает всю операцию.

## Конфигурация

Начните с [готовой конфигурации](../../examples/configs/README.ru.md): обычная проверка,
строгий CI, несколько входов, core, OSV или шаблон LLM-review. Для каждого файла
есть пример запуска и необходимые флаги разрешений.

Scout читает конфигурацию только по явному `--config`. Пример `/ci/scout.json`:

```json
{
  "schema": "scout.config/v1",
  "profile": "standard",
  "concurrency": {"targets": 1, "workers": 4},
  "timeout": "2m",
  "policy": {"fail_at": "high", "scope": "conservative"}
}
```

```sh
scout config validate --config /ci/scout.json
scout scan --config /ci/scout.json --format json ./my-plugin
```

Явные параметры переопределяют конфигурацию. Неуказанные поля получают значения по умолчанию;
неизвестные и повторяющиеся ключи отвергаются. Храните конфигурацию, baseline,
дополнительные правила и кеши вне проверяемых входов. См. [профили](inspection-profiles.ru.md).

## Сохранение отчётов

```sh
scout scan --format json \
  --report json=/ci-results/scout.json \
  --report sarif=/ci-results/scout.sarif \
  --fail-on high --timeout 2m ./skills ./plugins
scout scan --format markdown --output /ci-results/scout.md ./my-plugin
```

Форматы: `text`, `json`, `sarif`, `markdown`. Без `--output` основной отчёт идёт
в stdout. Повторяемый `--report FORMAT=PATH` добавляет другие представления.
Диагностика идёт в stderr. Создайте каталоги отчётов перед запуском.

Text и Markdown начинаются с решения, состояния запуска, числа находок по серьёзности
и пояснений причин политики. Находки идут перед служебными данными. Для пробелов
проверки указаны пути, объяснения и незавершённые обязательные задания; примечания
анализа вынесены отдельно. Захваченные файлы и извлечённые объекты посчитаны раздельно.
В Markdown служебные данные и общие ограничения идут под обычными заголовками,
значения — в обратных кавычках, без встроенного HTML-форматирования.
В сравнении первой показана новая версия, а её находки посчитаны отдельно
от предыдущей.
JSON и SARIF сохраняют полные машинные данные и стабильные идентификаторы.

Scout готовит каждый отчёт в приватном временном файле, затем заменяет назначение
переименованием. Ошибка подготовки сохраняет прежний файл. Символические ссылки, каталоги и пути
внутри проверяемых входов отвергаются. Несколько файлов публикуются независимо.

Коды завершения:

- `0`: полный запуск, политика разрешает установку, все отчёты записаны.
- `1`: полный запуск, политика требует ручной проверки или блокирует установку.
- `2`: неполный, неуспешный или отменённый запуск; неверный запрос; ошибка записи.

В CI сохраняйте отчёты и исходный код завершения. Консервативная область проверки
также требует ручной проверки при заявленных ограничениях языка.
См. [выбор области](inspection-profiles.ru.md#область-проверки).

## Baseline

Создайте baseline из JSON-отчёта с одним входом, проверьте записи и одобрите их:

```sh
scout baseline create --from /ci-results/scout.json \
  --output /ci-results/pending-baseline.json \
  --reason 'Manual triage required' --expires '2099-01-01T00:00:00Z'
scout baseline approve --from /ci-results/pending-baseline.json \
  --output /ci-results/reviewed-baseline.json \
  --reason 'Reviewed by operator' --expires '2099-01-01T00:00:00Z'
scout scan --baseline /ci-results/reviewed-baseline.json ./my-plugin
```

Выберите подходящий будущий срок в RFC3339. `create` сохраняет неодобренные записи;
`approve` одобряет все записи выбранного файла. Изменение идентичности требует
новой проверки. Исключения по маске требуют `--allow-baseline-globs`.
Находки остаются в отчёте; пробелы проверки и семантические гипотезы не подавляются.

## Сетевые сервисы и дополнительные rules

Сетевой вход требует `--allow-download`. Корень GitHub-репозитория также требует
`--revision` с полным commit SHA. См. [внешние источники](../reference/external-sources.ru.md).

```sh
scout scan --vuln --allow-vulnerability-network \
  --format json ./my-plugin
scout scan --vuln --osv-cache /ci/osv-cache.json \
  --osv-cache-max-age 168h --format json ./my-plugin
```

OSV проверяет точные координаты захваченных зависимостей. Кеш для работы без сети задаёт
оператор; отсутствующие и устаревшие записи оставляют пробелы проверки.
Запись об уязвимости не доказывает её достижимость в проверяемом коде.

### Известные вредоносные зависимости

Кеш оператора с `"version": 2` дополнительно включает `MAL001`.
Если точные координаты явно классифицированы как `malicious-package`, Scout создаёт
находку Critical с доказательством из захваченного manifest или lockfile. Версия 1
и записи без классификации по-прежнему используют `OSV001` (High). Префикс `MAL-`
в идентификаторе сам по себе не включает `MAL001`.

Используйте приведённую выше команду `--vuln --osv-cache FILE`. Доверенный кеш должен
находиться вне проверяемого входа. Ниже вымышленный пример схемы; перед использованием
замените его проверенными данными и фактическим временем запроса:

```json
{
  "version": 2,
  "queried_at": "2026-11-03T12:00:00Z",
  "records": [{
    "ecosystem": "npm",
    "name": "sample",
    "version": "1.2.3",
    "vulnerabilities": [{
      "id": "MAL-fixture",
      "kind": "malicious-package",
      "modified": "2026-11-03T11:00:00Z",
      "source": {
        "name": "operator-intel",
        "url": "https://example.invalid/intel/MAL-fixture",
        "revision": "snapshot-1"
      }
    }]
  }]
}
```

Производитель кеша должен проверить классификацию и затронутые версии в исходной
базе, затем сформировать ответы для точных ecosystem/name/version. Например,
[OpenSSF malicious-packages](https://github.com/ossf/malicious-packages) публикует
сообщения о вредоносных пакетах в [формате OSV](https://ossf.github.io/osv-schema/).
Scout не загружает эту базу и не импортирует диапазоны версий. Одного имени пакета,
его возраста или репутации издателя недостаточно для классификации malware.

Для каждой вредоносной записи обязательны `source.name`, `source.url`,
`source.revision` и время `modified` в RFC3339, не позднее `queried_at`.
Имя источника и ревизия — ограниченные ASCII-токены. URL требует HTTPS;
учётные данные, параметры запроса и фрагмент запрещены. Эти поля — утверждение оператора: Scout не проверяет
подлинность источника и не обращается к URL. JSON и SARIF сохраняют метаданные,
время запроса и SHA-256 переданного кеша; человекочитаемые отчёты показывают источник
и ревизию. Экспорт через `osv.Export` сохраняет версию 2, отрицательные ответы и
исходное время запроса. Время запроса классифицированного кеша входит в digest запуска.
При запечатывании отчёта и экспорте отклоняются противоречивое покрытие и вредоносные
совпадения без связи с проверенными по кешу координатами. Запросы в отчёте также
сверяются с инвентарём зависимостей. В `compare` кешированные ответы учитываются как
завершённые, если успешны все соответствующие проверки файла; успешная проверка
не скрывает пробел в другой.

Пустой массив `vulnerabilities` явно утверждает отрицательный результат проверки
точных координат для обоих видов advisories. Отсутствующие записи, неразрешённые
версии, будущий или устаревший кеш оставляют пробелы и не дают полного чистого
результата. Лимиты кеша: 256 КиБ, 4096 координат и 4096 записей advisory на координату.
Противоречивые метаданные одного ID для одних координат отклоняются. Это ограниченный
кеш запросов; полной встроенной базы malware нет.

Если также разрешена сеть, свежие ответы кеша версии 2 имеют приоритет.
OSV querybatch может добавить обычные уязвимости для отсутствующих координат,
но проверка malware остаётся с пробелом `classification_not_cached`.
Такие неполные координаты не экспортируются в кеш. Совпадение относится к захваченной
декларации и не доказывает установку или выполнение пакета.

### Версионируемые наборы правил

Пакет `scout.rulepack/v1` содержит дополнительные YARA-правила, идентификатор,
метку версии, ABI `scout.yara-source/v1` и SHA-256 исходника. Встроенные проверки
по-прежнему выбираются профилем. Формат переносит данные правил; новые анализаторы
на Go требуют релиза сканера. Пакет — явно выбранный локальный файл оператора
вне проверяемых входов.

```sh
scout rules pack create --id team/agent --version 1.2.3 \
  --yara /ci/agent.yar --output /ci/agent-1.2.3.rulepack.json
scout rules pack inspect /ci/agent-1.2.3.rulepack.json
scout scan --rulepack /ci/agent-1.2.3.rulepack.json \
  --rulepack-sha256 <trusted-64-digit-sha256> --format json ./my-plugin
```

Используйте хеш из доверенного процесса выпуска. Проверить закреплённый хеш перед
сканированием можно через `inspect --sha256 HASH`. Он охватывает все байты пакета:
ID, версию, ABI, хеш исходника и форматирование JSON. Встроенный хеш исходника
обнаруживает повреждение; тот, кто может заменить пакет, может заменить и этот хеш.
Оба хеша не подтверждают подлинность издателя.

Эквивалентная конфигурация:

```json
{
  "schema": "scout.config/v1",
  "signatures": {
    "rulepack_file": "/ci/agent-1.2.3.rulepack.json",
    "rulepack_sha256": "<trusted-64-digit-sha256>"
  }
}
```

Замените заглушку фактическим хешем в нижнем регистре. Профили standard и review
уже включают YARA. Для custom нужно выбрать `--checks yara`. Совместное применение
`--yara-rules` и `--rulepack` запрещено. Пакет не меняет профиль и не разрешает сеть.
Сканер не ищет пакеты внутри входов и не загружает обновления.

Для обновления выпустите новый пакет и явно смените путь вместе с закреплённым
хешем. Для отката выберите прежний пакет с его доверенным хешем. Созданный Scanner
владеет загруженным исходником: изменение файла или буфера вызывающего кода
не обновляет уже работающий экземпляр. Глобального состояния установки нет.

JSON/SARIF и человекочитаемые отчёты сохраняют ID, версию, ABI, хеш пакета и хеш
исходника в метаданных сигнатур. Пакет также входит в `RulepackDigest`: изменение
версии меняет этот отпечаток даже при одинаковом исходнике. Хеш объединённых
исходников сигнатур остаётся отдельным полем. Текст пакета не копируется в отчёт.

Создание и просмотр работают без нативного движка и не компилируют YARA. При запуске
сканер компилирует пакет до захвата входа; неподдержанная синтаксическая конструкция,
повторяющиеся имена правил, директивы include и модуль console завершают операцию ошибкой. Действуют текущие
лимиты и ограничения таймаутов YARA-X. И JSON-пакет, и исходник ограничены 256 КиБ;
экранирование JSON и метаданные занимают место в лимите пакета. Скомпилированные
бинарники YARA и исполняемые плагины через этот формат не загружаются.

`--yara-rules` добавляет доверенные правила оператора. Директивы include и вывод в консоль запрещены;
невалидные правила завершают операцию ошибкой. LLM требует отдельного
[согласия на передачу исходников](semantic-review.ru.md).
