# Измерение детекции

[English](evaluation.md) · Русский

`scout-dev evaluate` проверяет размеченный JSON-корпус через публичный Scanner API,
не исполняя код примеров. По умолчанию выполняется статическое сканирование без
сетевых сервисов. Отдельный необязательный прогон измеряет LLM-предположения через
явно настроенного провайдера.

```bash
# Reduced/core: built-in checks only.
CGO_ENABLED=0 go run -mod=readonly -tags=coreonly ./cmd/scout-dev evaluate \
  --profile custom testdata/security-corpus/cases.json
# Full native build with a trusted PKG_CONFIG_PATH:
CGO_ENABLED=1 go run -mod=readonly -tags=static_link ./cmd/scout-dev evaluate \
  --profile standard testdata/security-corpus/cases.json
```

Standard выбирает полный статический план. В этой команде custom включает только
встроенные проверки. `--timeout` ограничивает весь корпус. Формат задан в
`testdata/security-corpus/cases.json` (schema 1); один пример — один reader-файл.

## Пакеты и разделение выборок

В schema 2 каждый пример сканируется как каталог с несколькими обычными файлами.
Файлы создаются в приватном временном каталоге и удаляются после обоих режимов.
Флаг `executable` сохраняет метаданные для анализа; файлы не исполняются.
Тип, размер и executable-биты созданных файлов должны совпадать с корпусом.
Если файловая система не может их сохранить (включая executable-биты на Windows),
измерение завершается ошибкой. Корпус и конфигурация читаются только из обычных
файлов; FIFO и устройства отклоняются до чтения.
Пути должны быть относительными ASCII-путями без обхода каталогов, обратных
слешей, имён устройств Windows, различающихся только регистром имён, повторов
и конфликтов файла с каталогом. Содержимое допускает Unicode. Ограничения:
8 MiB JSON, 4096 примеров, 4096 источников, 1024 файла, 8192 файла/каталога суммарно
и 32 компонента пути на пакет. Пространство имён проверяется до создания временных
каталогов; обычные лимиты Scanner на захват и анализ продолжают действовать.
Файлы создаются с запретом перезаписи: псевдоним файловой системы не сможет
подменить уже записанный файл пакета.

```json
{
  "schema_version": 2,
  "kind": "independent_labelled_corpus",
  "sources": [{
    "id": "package-family-a",
    "origin": "https://example.invalid/repository-a",
    "revision": "reviewed-revision-or-source-sha256",
    "license": "MIT",
    "label_review": "Reviewer and labeling procedure; external evidence reference"
  }],
  "cases": [{
    "id": "package-a", "category": "documentation", "label": "benign",
    "source_id": "package-family-a", "split": "holdout",
    "expected_rules": [],
    "files": [
      {"path": "README.txt", "content": "Summarize the local notes.\n"},
      {"path": "references/notes.txt", "content": "Keep paragraph order.\n"}
    ]
  }]
}
```

Это пример формата, а не независимо проверенные данные. Для каждого источника
обязательны origin, зафиксированная ревизия или хеш, лицензия и запись о проверке
разметки. Форки, ревизии и связанные варианты объединяются одним source ID.
Один source ID или точный origin может принадлежать только одной выборке:
`train`, `tune`, `holdout`. Одинаковые непустые байты файлов в разных выборках
отклоняются даже при переименовании файлов. Общие шаблонные файлы нужно оставить
в одной выборке или исключить из корпуса. Повторяющиеся JSON-ключи и варианты
ключей с другим регистром отклоняются.

```bash
bin/scout-dev evaluate --split holdout testdata/security-corpus/packages.json > evaluation.json
```

Без `--split` измеряются все примеры с отдельными метриками каждой выборки.
До фильтрации проверяется **весь** корпус, включая невыбранные части.
Проверки не подтверждают подлинность происхождения, отсутствие смысловых
дубликатов, независимость от обучающих данных модели или правильность меток.
Встроенный `packages.json` содержит пять авторских примеров формата и регрессии;
его раздел `holdout` **не является независимым holdout**.

## Необязательное измерение LLM

Передайте доверенный `scout.config/v1` с явными провайдером `review`, endpoint,
моделью и лимитами; см. [конфигурацию](../user/usage.ru.md)
и [семантическую проверку](../user/semantic-review.ru.md).
`--llm-config` задаёт профиль сканера и несовместим с `--profile`.
Для reduced-сборки укажите `profile: custom` и явно отключите `patterns`,
`python`, `yaml`, `toml`, `yara` в `checks`. Встроенные проверки сохраняются.
Native-сборка может использовать `profile: standard` или `review`.

Пример `operator-review.json` (замените endpoint/model своим доверенным сервисом):

```json
{
  "schema": "scout.config/v1",
  "profile": "standard",
  "review": {
    "provider": "chat-completions",
    "endpoint": "https://reviewer.example.invalid/v1/chat/completions",
    "model": "operator-selected-model",
    "key_env": "SCOUT_EVAL_API_KEY",
    "max_requests": 16,
    "max_input_bytes": 262144,
    "max_output_tokens": 2048,
    "timeout": "30s"
  }
}
```

```bash
bin/scout-dev evaluate --llm-config operator-review.json --allow-source-upload \
  --split holdout --input-usd-per-million 2 --output-usd-per-million 4 \
  testdata/security-corpus/packages.json > evaluation-with-llm.json
```

Цены здесь — условные тарифы оператора в USD за миллион токенов, не актуальные
цены провайдера. Задайте оба тарифа или не задавайте ни одного. Учётные данные
читаются только из явно названных в конфигурации переменных. Не допускаются
провайдер по умолчанию, неявная передача исходников, OSV, загрузки, baseline,
дополнительный файл правил, advisory cache и remote pins. Evaluation использует
собственную политику с порогом high; пороги политики из конфига не меняют подсчёт
признаков.

Каждый пример сначала проверяется отдельным статическим Scanner с теми же
настройками, затем Scanner с включённым review. Верхнеуровневые метрики остаются
статическими. Метрики `llm` считают только валидированные предположения модели;
статические находки и подтверждения этих находок моделью не становятся LLM-детекцией.
Предположения остаются рекомендательными, даже если последующий проход модели
их оспаривает. Время LLM-прогона включает повторную статическую проверку и все
стадии review, а не только задержку провайдера. Лимиты review действуют на пример;
`--timeout` ограничивает весь корпус и оба режима.

## Метрики

- `signal` и `known_static_gap` — положительные случаи. Отсутствие находки считается
  пропуском, включая неполное сканирование.
- `benign` с находкой — ложное срабатывание. Полный benign без находок — верное отрицательное заключение; неполный результат остаётся неопределённым.
- `ambiguous` не включается в precision/recall.
- `false_positive_rate` = FP / (FP + полные benign без находок). Значение `null`
  означает отсутствие знаменателя или наличие неразрешённых benign-примеров.

Метрики используют метки и фактические находки; `expected_rules` задаёт ожидания
регрессии. Отчёт schema 2 хранит хеш корпуса, движок/rulepack и планы, результаты,
метрики категорий/выборок, число неполных проверок и локальные p50/p95.
Неопределённые отношения равны `null`. `selected_cases` и `completed` отличают
прерванное измерение от полного обхода выборки. При отмене готовые примеры
сохраняются с кодом выхода 2. Завершённое измерение возвращает 0 даже при сбоях
отдельных сканирований: сбои учитываются в метриках.

При LLM-проверке каждый пример хранит идентификатор провайдера, хеши prompt/schema,
эффективные настройки review и usage без исходного текста, URL endpoint или
сырых ошибок провайдера. `known_input_tokens` / `known_output_tokens` суммируют
числа от провайдера; отсутствие usage, сбои и невалидированные ответы делают
usage неполным. Стоимость равна `null` без обоих тарифов или полного usage.
Она не учитывает кэширование, скидки маршрутизации, минимальную оплату и налоги
и не заменяет счёт провайдера. Тесты используют синтетический протокольный
провайдер, а не настоящую модель.
Примеры без запланированных review-запросов остаются неразрешёнными в LLM-метриках.

Встроенные 26 авторских случаев — регрессионный корпус, не независимый holdout.
Для независимого измерения нужны отдельно проверенные исходники, метки, лицензии
и хеши с типом `independent_labelled_corpus`. Сохраняйте отчёт каждого запуска.
